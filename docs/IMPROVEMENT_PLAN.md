## 1. Самые опасные места (безопасность и потеря данных)

### 1.1. Устаревший Qt WebEngine 6.3.0 с сохраняемыми куками — CVE
`build.bat:5`, `.github/workflows/build.yml:33` — сборка жёстко на Qt 6.3.0 (Chromium ~94, 2021 год, EOL).
Приложение — это встроенный браузер, в котором пользователь **логинится в сервисы** (куки персистентны:
`WebViewContainer.cpp:63`). Все известные с 2021 года уязвимости Chromium применимы. Это худшее место в проекте.

### 1.2. Импорт пресетов = выполнение чужого JavaScript в авторизованных сессиях
`ResourceManager::importPresets()` принимает JSON с полями `initScript`/`openScript`/`altOpenScript`,
которые затем исполняются в контексте страниц, где пользователь залогинен (`WebViewContainer.cpp:174,205,226`).
Схема URL проверяется (только http/https — хорошо), но **скрипты не показываются пользователю при импорте**.
Импортировал «пресет для DeepL» из интернета — получил кражу сессии/куки. Нужно предупреждение с показом скриптов.

### 1.3. Неатомарная запись конфига — потеря всех настроек и ресурсов
`AppConfig::save()` (`AppConfig.cpp:85-98`) пишет напрямую в `settings.json` через `QFile::open(WriteOnly)`
(truncate). Крэш/выключение питания посреди записи → битый JSON → `load()` возвращает false →
приложение стартует с дефолтами → следующий `save()` **перезаписывает остатки**. Пользователь теряет все
ресурсы, скрипты и логины-настройки. Post-write верификация (строки 121-152) бесполезна: она проверяет уже
случившееся, а не предотвращает. Решение — `QSaveFile` (атомарный rename) + резервная копия при ошибке парсинга.

### 1.4. Лог-файл в текущей рабочей директории
`main.cpp:52` — `QDir::currentPath() + "/tinytools_log.txt"`. При автостарте из реестра CWD = `C:\Windows\System32`
→ открытие молча падает → всё логирование отключено именно тогда, когда оно нужно. При запуске из других мест —
мусорный файл где попало. Ротации нет, режим Append — файл растёт неограниченно (логируется каждый вход/выход из
каждой функции + консоль JS всех страниц: `WebViewContainer.cpp:44` — утечка содержимого страниц в plain-text файл).

### 1.5. Буфер обмена остаётся доступен странице навсегда
`WebViewContainer.cpp:170` — `window.tinyToolsClipboard = <текст>` внедряется в MainWorld и **не очищается**.
Любой скрипт страницы (включая сторонние аналитики/рекламу) может прочитать последний вставленный текст —
а это может быть пароль, оказавшийся в буфере. Минимум: очищать переменную после выполнения open-скрипта.

### 1.6. Тесты имеют побочные эффекты на реальной машине
- `test_config.cpp:69-83` пишет реальный файл в `%APPDATA%` (спасает только то, что путь зависит от имени exe — см. 2.1);
- `test_hotkey.cpp:46` регистрирует **настоящий глобальный хоткей** Ctrl+Shift+Alt+F12 на машине разработчика.
Нет `QStandardPaths::setTestModeEnabled(true)`.

## 2. Хрупкие места

### 2.1. Идентичность приложения зависит от имени exe-файла
`Constants::APP_NAME`/`ORGANIZATION_NAME` объявлены (`Constants.h:8-10`), но `setApplicationName()` /
`setOrganizationName()` **нигде не вызываются**. `QStandardPaths::AppDataLocation` тогда строится из имени
исполняемого файла. Переименовал `TinyTools.exe` → потерял конфиг, куки и все логины (профиль WebEngine
тоже там: `WebViewContainer.cpp:56`).

### 2.2. Каждое скрытие окна перерегистрирует глобальные хоткеи
Цепочка: `MainWindow::hideEvent()` → `config->save()` → `emit settingsChanged()` (`AppConfig.cpp:155`) →
`Application::onSettingsChanged()` → `updateAllHotkeys()` → Unregister+RegisterHotKey.
Окно скрывается **каждым нажатием хоткея** — то есть на каждый toggle идёт полный цикл перерегистрации
хоткеев + переустановка темы во все WebView. Если в этот момент другой процесс успел занять комбинацию,
хоткей молча теряется до перезапуска. `save()` не должен эмитить `settingsChanged` при сохранении геометрии.

### 2.3. Каждый тик Ctrl+колесо перестраивает все табы
`MainWindow::onZoomChanged()` → `updateResource()` → `resourcesChanged` → `refreshResources()` →
снос и пересоздание всех табов на каждый шаг зума. Дебаунс на диск есть, но сигнальный шторм — нет.
Нужен тихий апдейт зума (без `resourcesChanged`) или отдельный сигнал.

### 2.4. Утечка Chromium-страницы при удалении ресурса
`MainWindow::m_resourceViews` никогда не чистится при `resourceRemoved`. Удалённый ресурс оставляет живой
`WebViewContainer` (целый рендер-процесс Chromium, десятки МБ) в `m_stackedWidget` до выхода из приложения.

### 2.5. Правка URL/initScript не применяется к открытой вкладке
`loadCurrentResource()` создаёт view один раз; `refreshResources()` обновляет только имена табов.
Поменял URL ресурса в настройках → вкладка продолжает показывать старый сайт до перезапуска приложения.
`m_initScript` тоже кэшируется на момент `loadResource` (`WebViewContainer.cpp:114`).

### 2.6. Бесконечный цикл перезагрузки упавшего рендера
`onRenderProcessTerminated()` (`WebViewContainer.cpp:265`) — безусловный `reload()` через 1 с.
Если страница стабильно роняет рендер, получаем вечный crash-reload-loop без backoff и лимита.

### 2.7. «Always on Top = false» игнорируется при старте
`setupWindowFlags()` всегда ставит `Qt::WindowStaysOnTopHint` (`MainWindow.cpp:208`), конструктор только
**добавляет** флаг при `getAlwaysOnTop()==true`, но никогда не снимает при false. Окно всегда поверх всех
до первого захода в настройки.

### 2.8. Мёртвый код (удалить)
- `src/app/Utils.h` — 160 строк деклараций **без единой реализации**; содержит несуществующий тип `QTuple`
  (строка 158) — файл сломает компиляцию первому, кто его включит. Не включён нигде.
- `src/models/TranslationRequest.h`, `src/tray/TrayMenu.h` — классы без .cpp, не используются.
- `NetworkMonitor` — заглушка: `onlineStatusChanged` никогда не эмитится, `startMonitoring()` никто не вызывает.
  Весь offline-путь (`MainWindow::setOnlineStatus`, «Offline» HTML) мёртв.
- Resource-хоткеи в `HotkeyManager` (~120 строк: `registerResourceHotkey`, `resourceHotkeyPressed`,
  `unregisterResourceHotkeys`) — никто не вызывает и не подключает.
- `autoTranslate`: чекбокс удалён из UI (`SettingsDialog.cpp:220`), включить настройку нельзя → ветки в
  `MainWindow::onClipboardChanged` и `TrayIcon::onShowWindow` недостижимы.
- `TrayIcon::showNotification()` — не вызывается (а зря, см. 3.2).
- Половина `Constants.h` не используется (`APP_NAME`, `WEBVIEW_LOAD_TIMEOUT_MS`, `NETWORK_CHECK_INTERVAL_MS`,
  ICON_*, ERROR_*, LOG_CATEGORY_*).

### 2.9. Артефакты LLM-генерации в коде
- `MainWindow.cpp:373-377` — комментарий «I will copy them back to ensure file completeness... For brevity
  in this tool call...» — прямо в продакшн-коде.
- `SettingsDialog.cpp:556-557, 643-644, 746-747` — трижды продублированные строки
  (`setChecked(getDarkTheme())` два раза подряд и т.п.).
- `SettingsDialog.cpp:458, 576` — комментарии-заглушки «// ... in SettingsDialog methods ...».

### 2.10. Тотальное ENTRY/EXIT-логирование
Едва ли не каждая функция пишет 2-10 строк `qDebug` на вызов (например, `ClipboardManager::getText()` —
6 строк на каждое чтение буфера). Это ~40% всего кода: шумит, тормозит (каждая строка — mutex + flush на диск,
`main.cpp:46`), раздувает лог. Оставить `qInfo`/`qWarning` на значимых событиях, debug-уровень — под флагом.

## 3. Не-юзерфрендли места

### 3.1. Ошибки загрузки страницы невидимы
Сигнал `WebViewContainer::loadError` **никуда не подключён**. Опечатка в URL, упавший сайт, нет сети —
пользователь видит просто пустую/белую вкладку без объяснений и кнопки Retry.

### 3.2. Ошибка регистрации хоткея — молча в лог
`RegisterHotKey` часто падает из-за конфликта с другим приложением (`HotkeyManager.cpp:210-216` — только
qCritical в лог). Пользователь уверен, что всё работает, а хоткей мёртв. Нужен tray-balloon
(`showNotification` уже написан!) и индикация в настройках.

### 3.3. Можно записать глобальный хоткей без модификаторов
`HotkeyEdit::eventFilter` принимает голую букву (например, `T`) как хоткей. RegisterHotKey с 0 модификаторов
**глобально перехватит букву T во всех приложениях Windows**. Также нет проверки конфликта Main vs Alt хоткея.
Требовать хотя бы один модификатор + конфликт-чек.

### 3.4. Настройка «Minimize to Tray» ни на что не влияет
`closeEvent()` всегда `hide()` (`MainWindow.cpp:650-653`), независимо от чекбокса. Выйти из приложения можно
**только** через меню трея; если системный трей недоступен — приложение неубиваемо без диспетчера задач.

### 3.5. Cancel в настройках откатывает не всё
Добавление/удаление ресурса применяется к `ResourceManager` немедленно, до OK (`SettingsDialog.cpp:480,488`).
Нажал Cancel — ресурс всё равно исчез из табов, но на диске остался → «воскресает» после перезапуска.
Остальные настройки при Cancel честно откатываются. Непоследовательно и ведёт к рассинхрону память/диск.

### 3.6. Ресурс нельзя выключить из UI
`WebResource.isEnabled` учитывается табами, но в панели ресурса нет чекбокса — выключить можно только ручной
правкой settings.json.

### 3.7. «New Resource» создаётся с URL `https://`
Проходит валидацию схемы (`WebResource::isValid`), создаёт вкладку, которая никогда не загрузится. Валидировать
наличие хоста; подсвечивать невалидный URL в панели.

### 3.8. Смена темы не применяется к уже открытой странице
Тема ставится скриптом `DocumentCreation` (`WebViewContainer.cpp:348`) — вступает в силу только при следующей
навигации. Переключил Dark Theme → страницы выглядят по-старому до ручного F5.

### 3.9. README обещает «unlimited web resources»
Импорт обрезается на `MAX_RESOURCES = 10`, при этом ручное добавление не ограничено ничем. Синхронизировать
документацию и поведение.

## 4. Что не покрыто тестами (но стоит покрыть)

**Главное: CI собирает проект, но не запускает тесты вообще** — в `build.yml` нет шага `ctest`.
Тесты существуют, зелёный бейдж есть, а регрессии никто не ловит.

Приоритетные кандидаты (чистая логика, тестируется дёшево):

| Область | Что тестировать | Почему |
|---|---|---|
| `HotkeyEdit` | round-trip `parseHotkeyString` ↔ `hotkeyString`, именованные клавиши, отказ от «голых» хоткеев | 350 строк ручного парсинга, 0 тестов |
| `AppConfig` | сериализация хоткея с модификаторами (set→save→load→get); битый JSON → load()==false и данные не затираются; qBound-границы opacity/размеров | защита от потери данных (п. 1.3) |
| `ResourceManager` | round-trip `saveToConfig`/`loadFromConfig`; `reorderResources` (в т.ч. id не из списка); `getStartupResource` fallback-логика; регенерация дублирующихся id при импорте | персистентность — ядро продукта |
| `ClipboardManager` | `onClipboardChanged` эмитит только при изменении и валидном тексте (QSignalSpy); фильтрация картинок | сигнальная логика не покрыта |
| `WebResource` | `fromJson` с отсутствующими полями; `isValid` краевые случаи: `https://` без хоста, `JAVASCRIPT:`, `file://` в верхнем регистре | входная валидация — security-граница |
| Атомарность конфига | после перехода на QSaveFile: имитация битого файла → бэкап создан, дефолты не перезаписали бэкап | п. 1.3 |

Существующие тесты, требующие ремонта:
- `tests/integration/test_webview.cpp` — не подключён к CMake, создаёт **второй** QApplication поверх QTEST_MAIN,
  содержит бессмысленный `QVERIFY(&webView != nullptr)` (всегда true). Починить или удалить.
- Все тесты: добавить `QStandardPaths::setTestModeEnabled(true)` (изоляция от реального %APPDATA%).
- `test_logging` тестирует копию обработчика, а не реальный из main.cpp — вынести обработчик в отдельный
  модуль и тестировать его.
